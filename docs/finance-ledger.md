# 実費配分による精算台帳（初版）

## 合意した仕様

- 精算区分は「1日目のロケ」などのまとまり。参加費は区分ごとの概算請求。
- 実際の経費を対象者へ重み（小数第3位まで）または整数円の直接指定で配分する。
- 費目は配分設定の再利用に使う。経費にコピーして保存するため、費目や回答を変えても過去の経費を上書きしない。
- カンパ等は別途指定した対象者への負担軽減。提供者への返金権とは結び付けない。
- 協力金は経費負担と受取人を分ける。立替経費は実費を負担に加え、立替者に同額の返済予定を付ける。
- イベント資金への一時的な貸付・返済はシステム外で管理する。
- 帽子代などは独立請求。イベントの実費精算から除外し、資金残高では別会計分を分けて表示する。
- 請求・徴収・精算・返金は並行可能。確定は計算結果の保存であり、全体をロックしない。
- 誤入力は元の入出金を編集・削除する。変更履歴は収支に加算しない。
- 手動調整は増減額か最終返金総額の指定のいずれか。固定総額は再計算後も維持する。

## 計算と確定

個人の自動返金総額（丸め前）:

`概算参加費請求額 − 経費負担 ＋ その他収入の配分 ＋ 協力金・立替返済`

費目ごとには丸めず、区分を合算した後、個人の総額を指定単位で切り捨てる。配分計算はBigIntの有理数で行う。手動調整は丸め後に適用し、指定した整数円を維持する。

確定時には `概算参加費請求額 − 調整後返金総額` を、その人の最終負担として保存する。

受け渡し残額:

`参加費の実受領額 ＋ 精算で追加徴収した額 − 支払済額 − 確定した最終負担`

正は支払い、負は追加徴収。全額の概算参加費を受け取っていなくても精算できる。帽子代等の独立請求は別に未収額を管理する。

- 未配分の経費・収入があれば確定できない。負担対象が全員0の場合も未配分として表示。
- 確定後の条件変更は計算案に反映し、「前回から変更あり」と表示する。受け渡しは前回確定額を使用し、再確定で新しい額を採用する。
- 入出金の追加・訂正だけでは精算条件は変わらず、残額が直ちに変わる。
- 新しい返金・追加徴収の記録は、確定した残額を上限にする。実際の過去の記録を訂正した結果の過払いは、要回収として残る。
- 参加費を徴収した後でも概算請求を変更できる。実受領額は書き換えない。
- 概算請求の未収額と精算の追加徴収額は別表示。両方を二重徴収しないよう画面で説明する。

## 入力と権限

既存の4領域を維持する。

| 領域 | 編集・記録の範囲 | 確定 |
|---|---|---|
| 参加費計算 | 精算区分、対象者、参加費請求、独立請求 | 保存後すぐ徴収可能 |
| 参加費徴収 | 請求への入金、精算による追加徴収、訂正・削除 | なし |
| 経費精算 | 区分別の費目、経費、収入、配分、協力金、参加者による経費立替、別会計支払い、手動調整、関連入出金 | 精算確定・端数単位変更 |
| 返金 | 参加者への精算金支払い（協力金・立替返済を含む）、訂正・削除 | なし |

閲覧用APIと履歴も権限で明細を制限する。経費等の登録と支払済み／受領済み記録は同時保存できる。

参加可否質問に対応する精算区分と、その対象者の基本請求を自動作成する。区分名・対象者・基本請求の有効性は質問と回答に連動し、質問区分の対象者や基本請求だけを精算画面から追加・削除できない。手動区分の対象者は区分設定で変更する。基本請求作成ボタンは不要。

- 基本請求は1人×1区分につき1件。基本金額に追従するか、個別金額（0を含む）を指定する。
- 質問に紐づく区分は質問順で表示し、手動区分はその後に表示する。表示順だけの変更で精算確定を無効にしない。
- 質問に紐づく区分の基本金額は精算区分の表で直接入力し、フォーカスを外すかEnterで保存する。保存失敗時は入力額を保持する。手動区分は名前・金額・対象者をダイアログで編集し、質問回答からの一時コピーは行わない。
- 自分の保存結果は自動反映する。他の担当者の更新や新しい参加回答を取り込むための「再読み込み」は残す。
- 不参加になると基本請求の有効額は0になる。請求ID・個別指定・入出金・経費配分は維持し、再参加で同じ基本請求と個別設定を再適用する。
- 質問のアーカイブは不参加扱いにせず、対象者と請求を維持する。
- 一覧表は参加者×区分の基本請求、追加請求合計、総額を表示する。各セルに操作ボタンを置かず、参加者名・編集アイコンからその人の請求を縦に編集する。
- 個別指定は赤字と「＊」で示す。基本金額と同額でも印を付ける。対象外に入金が残る場合は「対象外・入金あり」と表示する。
- 参加者別編集は基本金額／個別金額・調整メモ・追加請求をまとめて保存し、失敗時は全部取り消す。参加者・基本請求の区分は固定。閲覧権限のみでも内訳を確認できる。
- 追加請求は基本請求とは別明細。区分を指定すればイベント精算に含め、区分なしなら別会計。入金済みの追加請求は削除・区分変更できない。
- 請求の保存は直ちに徴収予定額へ反映するが、過去の入出金を変更しない。返金額を採用する精算確定は引き続き必要。


## 永続化・移行

- 旧Settlement系テーブルは移行元として残す。現在データは正規化テーブルに保存し、JSONは `FinanceLedgerHistory.state` の履歴にのみ使用する。
- `FinanceLedgerHistory` に変更ごとの状態、操作者、日時、操作IDを保存する。計算確定時の根拠も履歴に残る。
- 版番号による楽観ロックと、状態・履歴を同じDBトランザクションに保存することで同時更新を検出する。操作IDの再送では再記録しない。
- 回答への外部キーに依存せず参加者ID・名前を保存し、回答削除でも新台帳の記録を残す。
- 旧精算データのないイベントは自動で新方式を開始する。旧データがある場合のみプレビューを表示し、主催者が確認後に切り替える。
- 旧方式の確定返金額・返金実績を維持する。新しい計算額は再確定するまで採用しない。
- 徴収済みフラグは保存済みの請求総額を各請求へ充当する。不整合があれば移行メモに表示。
- 旧経費は支出済みとして計上する。その他収入の受領状況は復元できないため確認して受領を登録する。
- 切替は旧財務への書込みとDBロックで排他する。切替後はAPIとDBトリガーの両方で旧財務への書込みを拒否する。イベント・回答削除に伴う安全なカスケードは許可する。

### 現在データの保存先

| テーブル | 内容 |
|---|---|
| `FinanceLedger` | イベント単位の版番号・丸め単位・精算確定日時（JSONなし） |
| `FinancePerson` | 精算対象者。回答を削除しても金銭記録の対象者を維持 |
| `FinanceCategory` / `FinanceCategoryMember` | 精算区分、質問との紐づけ、基本参加費、対象者 |
| `FinanceCharge` | 参加者別請求。`isBase` で基本請求と追加請求を区別し、基本請求は `(eventId, categoryId, personId)` の部分一意制約を持つ。`amountOverride = NULL` は区分の基本参加費に追従、整数値（0を含む）は個別指定 |
| `FinanceItem` / `FinanceItemAllocation` | 費目と配分テンプレート |
| `FinanceExpense` / `FinanceExpenseAllocation` / `FinanceExpenseRecipient` | 経費・費用配分・協力金受取人 |
| `FinanceIncome` / `FinanceIncomeAllocation` | その他収入と負担軽減配分 |
| `FinanceAdjustment` | 手動調整 |
| `FinancePayment` | 実際の入出金。請求・人・経費・収入への専用外部キー |
| `FinanceSettlementTarget` | 確定した個人別の最終負担額 |
| `FinanceMigrationNote` | 移行時の確認事項 |
| `FinanceLedgerHistory` | 操作・操作者・版番号・操作後状態（ここだけJSON） |

区分には `(eventId, questionId)` の一意制約を設け、質問・区分・明細の参照は同一イベント内の複合外部キーで制約する。入出金は種類に対応する参照を1つだけ持つCHECK制約も設ける。個別の配分合計などの業務ルールはドメイン検証も併用する。

初回閲覧時の区分自動作成と、質問・回答変更の同期は、イベント単位のDBロック内で現在テーブルと履歴に保存してから返す。既存の区分は質問IDで特定し、名前変更でも同じIDと金額を維持する。未保存の区分を表示用に追加しない。新方式の通常操作・初期化・旧方式切替は同じロックを使い、版番号チェックも併用する。

`20260929000000_normalize_finance` は、許可された実験段階のFinanceLedgerデータとその履歴を破棄する。旧Settlement系データは変更せず、旧方式からの明示的な切替で正規化テーブルへ移す。FinanceLedgerのJSONからの移行は行わない。`20260929001000_finance_question_cascade` は質問への外部キーを遅延検証にし、イベント全体の削除時は質問・台帳双方の削除完了後に整合性を検証する。質問単独の削除で金銭記録は消えない。`20260930000000_automatic_base_charges` は既存の区分別請求のうち1件を基本請求として識別し、残りを追加請求として保持する。金額・ID・入出金は破棄しない。変更履歴画面は直近100版を表示する。

## 初版レビュー手順

**ここでレビュー：入力負担と、残額の分かりやすさを確認する。**

1. 参加費管理を開き、旧データの移行メモと引継ぎ結果を確認する。
2. 確認用のイベントで新方式へ切り替える。
3. 1日目の区分を作り、3人に基本参加費4,000円を請求する。
4. 徴収画面でそれぞれ4,000円の入金を記録する。
5. フェリー6,000円を重み1・1・0、更衣室1,250円を1・1・0.5で登録する。
6. 返金案が500円・500円・3,750円になることを確認し、確定する。
7. Aへ500円を支払い、カンパ900円を3人へ均等配分して再確定する。Aの追加返金が300円になることを確認する。
8. Cの最終総額を2,000円に固定し、他の経費変更後も維持されることを確認する。
9. 入金の800円→8,000円訂正を試し、訂正履歴と残額を確認する。
10. 帽子代と参加者による経費立替も登録し、別会計分と参加者への支払額を確認する。

レビュー対象は、費目の配分入力、徴収と精算の切替、最終総額指定と今回支払額の違い、確定操作の必要性、スマートフォンでの操作量。

## フロントエンドの構成

`apps/frontend/src/features/participantManagement/pages/finance/ledger` に配置する。

- `LedgerWorkspace.vue` は画面の選択、編集対象、削除・精算確定・旧方式切替の確認を管理する。
- `useLedgerSession.ts` はWorkspaceごとに一つ作成し、台帳取得、権限判定、更新コマンド、リビジョン、処理中・エラー状態、変更履歴取得を共有する。各画面が別々の台帳やAPI更新処理を持たない。イベント間で共有するグローバル状態にはしない。
- `LedgerCalculationPanel`、`LedgerCollectionPanel`、`LedgerSettlementPanel`、`LedgerTransferPanel` が計算・徴収・経費精算・返金を担当する。編集・削除の要求は親へイベントで通知する。画面を切り替えても検索条件や開いた参加者の内訳を保持する。
- `LedgerPaymentHistory` と `LedgerChangeHistory` は実際の受け渡し履歴と操作履歴の表示を分担する。更新成功時の履歴キャッシュ破棄はSessionで行う。
- `LedgerEditor.vue` は入力対象に対応するフォームを選ぶ。それぞれのEditorが対象に必要な入力状態と保存データを持つ。`LedgerFormShell` はダイアログ枠・エラー表示・保存ボタンを共有し、`ImmediatePaymentFields` と `payment-record-fields.ts` は明細と同時に記録する入出金の入力・組み立てを共有する。
- 台帳画面のボタンは共通の `MyButton` を使う。フォーム送信と通常操作の `type` を明示する。
- 金額計算・保存時の業務ルールは引き続きcoreとバックエンドが担当する。表示用の金額整形は `ledger-display.ts` に置く。

## 検証

- 計算・権限・保存サービスの自動テスト。
- 実DBの全明細の保存・復元、基本金額への追従、外部キー・一意・CHECK制約、旧方式からの移行、版番号による更新拒否を、全書込みロールバック付きで検証。
- Playwrightによる独立した確認用データでの操作テスト（本番APIの認証テストとは別）：実費配分、精算確定、返金、追加カンパ、最終額指定、回答取込み、390px幅の表示。
- 実サービス経由の同時初期化・再読込・旧方式の切替・イベント削除を、専用の一時イベント（finallyで削除）で検証。
- 型検査、変更ファイルの静的検査、全体ビルド。

DBスキーマのマイグレーションは開発環境へ適用済み。既存イベントの台帳切替は実施していない。本番への適用と実イベントの切替は、初版レビューと移行確認の後に行う。

### 参加費徴収の操作

通常は参加者の行のチェックで予定残額を現金受領する。「未収がある人だけ」と名前検索で対象を絞れる。一部だけ受領する場合は、その人の「個別入金」から記録する。個別入金画面では区分ごとの参加費明細と合計を先に表示する。対象は本人の未収請求だけで、複数あるときだけ請求を選ぶ。部分入金は請求明細ごとに記録する。業者や収入の操作はこの画面に出さない。

確定精算の追加徴収は別枠に表示する。参加費の未収を含む精算後の残額なので、通常の予定額とは合算しない。追加徴収を記録した人の通常徴収は止め、別会計の未収だけ引き続き個別に受領できる。入金履歴は通常は折りたたみ、訂正時に開く。訂正でも対象・種類を変更させない。

### 経費精算の操作

精算区分ごとに参加費・その他収入と経費をまとめて表示し、その区分の「経費を追加」「収入を追加」から入力する。経費は保存額を支出として直接計上する。その他収入の未受領額は各明細の「受け取る」から対象を固定して記録する。対象のない汎用的な「入出金を記録」は設けない。別会計の支払いは独立した欄に表示する。イベント資金への一時的な貸付・返済はシステム外で扱い、台帳の明細・入出金種別・残高計算には含めない。

### 2026-10-03 経費精算の簡略化

- 区分の収入に参加費請求額（個別調整を含む）を表示し、徴収済み額を併記する。収入合計・支出合計・請求額ベースの差額を表示する。
- 収入は左、支出は右。スマホでは収入、支出の順。区分見出しと入力画面の区分名はスクロール中も固定表示する。
- 経費は登録した時点で支出として扱う。支払い日時・未払い状態は管理しない。保存・訂正・削除が資金残高へ直接反映される。従来の経費支払い記録は二重計上しない。経費編集時に旧支払い明細を取り除き、履歴JSONに訂正前の状態を残す。
- 参加者の立替経費と協力金は参加者への精算に含めるため、経費保存時にイベント資金から差し引かない。
- 費目テンプレートの新規作成・選択は通常UIから外す。既存の経費の配分設定は保持する。
- 配分は区分参加者が重み1、区分外は0が初期値。個別設定チェック時だけ入力欄を開き、保存済みのカスタム設定は編集時に表示する。
- 協力金は受取人の選択と1人あたりの金額から総額を計算する。個別額はチェック時のみ入力する。

### 2026-10-06: 保存内容を返金・追加徴収へ即反映

- 精算確定の UI を撤去し、保存済みの請求・経費・収入・調整・丸め設定から返金予定額を計算する。
- 受け渡し残額は、参加費受領 + 追加徴収済み - 返金済み - 最新の負担額。入出金実績は再計算で変更しない。
- 未配分明細がある場合は受け渡し残額を利用不可とし、新規返金・追加徴収を拒否する。
- 保存 revision の競合に加え、記録直前の参加回答同期で変更が見つかった場合も返金・追加徴収を拒否し、再読み込みと最新額の確認を要求する。
- 切捨て単位の変更は settlement:edit、返金記録は従来の refund:record 権限で行う。
- 旧 snapshot と confirm コマンドは過去記録・旧クライアント互換のため保持するが、snapshot の金額は現在の返金計算に使用しない。
